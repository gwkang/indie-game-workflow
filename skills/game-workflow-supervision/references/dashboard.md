# 프로젝트 개발 대시보드

대시보드는 워크플로 적용 프로젝트의 기본 결과물이다. 사용자에게 프로젝트 폴더를 입력하도록 요구하지 않는다. 설치된 [도구](../scripts/dashboard.py)의 위치에서 소속 프로젝트를 찾는다. 공통 도구·화면은 스킬에, 설정·요약·실행 도구는 프로젝트에 둔다. Python 3.12 이상 표준 라이브러리만 사용한다. 도구 설치나 외부 게시 권한은 포함하지 않는다.

## 처음 생성하고 열기

프로젝트에 워크플로를 적용할 때 프로젝트 설정 담당자가 이름과 실제 기록 경로를 연결한다. 기본값은 `planning/game-workflow-profile.md`와 `planning/workflow-runs/active.json`이다. 다른 경로를 사용하는 프로젝트는 `init --profile ... --registry ... --name ...` 또는 생성된 설정에 실제 값을 남긴다. 누락된 기본 자료는 ‘아직 작업 없음’으로 시작하며 제품·엔진·규칙을 만들지 않는다. 자료가 있는데 해석에 실패하면 초기 생성 실패로 보고한다.

```powershell
python -B .agents/skills/game-workflow-supervision/scripts/dashboard.py init
python -B planning/workflow-dashboard/open.py
```

소속 프로젝트가 이미 정해진 실행 도구를 어느 폴더에서 실행해도 같은 프로젝트가 열린다. 서버는 127.0.0.1의 빈 포트를 사용하고 주소를 출력한다. `--no-browser`는 주소만 출력하고, `--port 숫자`는 특정 포트를 사용한다. 사용 중인 서버를 종료하거나 대체하지 않는다. 실행 창에서 Ctrl+C로 종료한다.

## 기록 갱신

새 요청·재개 때 프로젝트 연결과 설정을 확인한다. 없으면 허용된 적용 범위에서 초기 생성한다. 기존 설정은 보존한다. 감독이 작업 배정·반환·수정·결정·검사 버전을 원본 기록에 반영한 다음 실행한다.

```powershell
python -B planning/workflow-dashboard/open.py update
```

마무리 때 성공한 명령·현재 기록의 지문과 열어 볼 경로를 보고한다. 생성·갱신 실패는 대시보드 문제이며 게임 결함으로 판단하지 않는다. 최초 생성이 필수인 적용에서는 실패를 완료로 보고하지 않는다. 사용자가 제외를 명시하면 프로젝트 적용 기록에 이유를 남긴다.

서버는 화면 요청마다 기록을 읽어 메모리에서 표시한다. 화면은 5초마다 다시 읽는다. 서버는 원본 기록과 저장된 요약을 쓰지 않으며, 감독의 `update`만 저장된 요약을 단일 교체한다. 이 절차는 여러 파일의 동시 거래·자동 작업자 감시·충돌 복구 기능이 아니다. 실패하면 마지막 정상 내용과 오래된 기록 안내를 보여준다.

## 자료와 의미

- `dashboard.config.json`: 프로젝트 고유 번호·이름·소속 경로·자료 경로. 프로젝트의 수동 설정을 덮어쓰지 않는다. 다른 프로젝트의 설정은 거부한다. 이동·복사한 프로젝트를 명시적으로 다시 연결할 때만 `init --rebind`를 사용하며 기존 설정을 별도 보존한다.
- `snapshot.json`: 원본의 파일 지문·읽은 시각·출처를 가진 파생 요약. 완료/승인/작업 상태의 원본이 아니다. 서버가 임의 파일을 제공하지 않으며 설정된 기록만 프로젝트 안에서 읽는다.
- 레지스트리 schemaVersion1의 `runId`, `recordPath`, `status`, `goalRevision`을 읽는다. 상태는 ‘등록 상태’로 표시한다. 작업 기록의 마지막 명시적 `Current checkpoint` 또는 `현재 체크포인트`와 `Tasks`/작업 표를 읽고 해석되지 않는 내용은 원문으로 남긴다.
- 작업 표의 상태·검사 결과·증거 유효성은 별도 열로 표시한다. `completed`는 작업 종료이며 `pass`와 다르다. 현재 검사 결과가 없는 과거 PASS를 가져오지 않는다. `Skill/owner`는 배정 기록이다. `Consumed skills`/`사용 기록`의 `Skill`, `Task`, `Usage` 열에서 `consumed`/`사용 확인`/`실제 사용`인 것만 실제 사용으로 표시한다. 그 외는 계획이다.
- `Repair`/`Findings`/`발견된 문제` 표에서 설명·상태·다음 행동을 읽는다. 표가 없다는 이유로 문제가 없다고 결론내리지 않는다. 낯선 형식과 상태는 미확인이다.
- 원문은 텍스트로만 표시한다. 명시된 기록 경로 이외의 파일·외부 링크·사용자 저장을 읽지 않는다. 4MiB보다 큰 기록은 분리한 자료를 연결한다.

## 전체 개발 범위

개발 목록 연결은 필수다. 목록이 없으면 준비 미완료이며, 전체 범위가 `scopeState:unknown`이면 부분 항목이 있어도 ‘전체 범위 미정’과 percent=null을 유지한다. 작업 수나 작업 종료 수를 전체 게임 완료율로 만들지 않는다. 범위가 실제로 정해진 프로젝트만 설정의 `roadmapPath`에 프로젝트 안의 JSON을 연결한다. schemaVersion1, `scopeRevision`, `items`를 사용한다. 항목은 아래 형식이다. 이 예시는 형식 설명이며 실제 완료 근거가 아니다.

```json
{
  "schemaVersion": 1,
  "scopeRevision": "범위-1",
  "items": [{
    "id": "개발항목-1",
    "title": "정해진 개발 목표",
    "inScope": true,
    "acceptanceState": "pending",
    "candidate": {"id": "검사버전-1", "digest": "현재 버전의 SHA-256 64자리"},
    "criteria": [{
      "id": "검사-1", "verdict": "unknown", "validity": "unknown",
      "candidateDigest": "검사한 버전의 SHA-256 64자리",
      "producerId": "작성자", "verifierId": "별도 검사자", "evidenceLocator": "실제 근거 위치"
    }],
    "decisions": []
  }]
}
```

완료 집계는 `accepted` 항목에 대해 모든 필수 검사 `pass/current`, 같은 버전 지문, 서로 다른 작성자/검사자와 근거 위치를 요구한다. 필요한 승인 목록은 `state: approved`, 같은 `candidateDigest`, `authorityLocator`를 가진다. 필요 승인이 없으면 `decisions: []`로 명시한다. 누락/중복 목록은 산정 오류이며 마지막 정상 자료가 있으면 오래됨으로 표시한다. skipped/cancelled는 완료가 아니다. 제외는 명시적 `inScope: false`만 사용한다. 같은 비중의 완료 항목 수/범위 안 항목 수이며 기간·작업량 추정이나 가중치 계산은 제공하지 않는다. 목록 작성자와 감독이 실제 근거 위치의 적합성을 소유한다. 도구는 근거 파일의 내용·승인 권한을 새로 판정하지 않는다.

## 배포·업데이트

공용 묶음에는 이 지침과 도구·웹 자산·스킬 연결·설치 도구를 넣는다. 프로젝트 이름·설정·절대 경로·작업 기록·요약은 넣지 않는다. 기존 공식 lock은 출처를 유지하고 로컬 delta는 별도 manifest로 기록한다. 공용 버전을 게시할 때 원본 bundle/lock을 같은 후보로 갱신한 뒤 격리 설치·초기 생성·재사용을 검증한다. 프로젝트는 해당 버전으로 업데이트해야 사용하며 다른 프로젝트를 자동 갱신하지 않는다.

## 상태 도구의 작업 기록

[공용 상태 도구](run-state.md)를 선택한 새 실행의 `recordPath`는 workflow-run schemaVersion1 JSON이다. 기존 Markdown은 계속 기존 방식으로 읽는다. JSON의 현재 단계·막힌 이유·다음 행동·작업·실제 사용 스킬·검사·별도 검토를 같은 원본에서 보여준다. 파일·근거가 바뀌면 개별 결과가 오래됨으로 표시되며, 상태 JSON 읽기 자체의 실패는 마지막 정상 요약과 구분한다. 등록 상태와 실제 기록 상태가 다르면 연결 확인 필요로 표시한다. 대시보드는 완료/승인 상태를 쓰지 않는다. 후보·검사 근거를 확인해도 해당 파일을 원문 제공 경로에 자동 추가하지 않는다. run/task 수를 전체 개발 완료율로 만들지 않는다.
