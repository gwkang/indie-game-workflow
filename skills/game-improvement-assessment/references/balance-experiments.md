# Balance experiments

Use for difficulty, rewards, prices or pacing changes. Keep the experiment in the existing assessment/work record; this reference adds no approval stage or separate report.

## Define before changing values

- State one falsifiable hypothesis linked to an observed player symptom. Name a signal that would count against it; do not invent a numerical target without a basis.
- Bound the variables and candidate values. Identify retained rules/constraints and the exact baseline values to restore. If several variables change together, treat them as a combined candidate rather than attributing the effect to one variable.
- Identify each candidate by a stable ID and its exact values plus build/configuration. Keep proposed values distinct from the authorized active configuration.
- Choose comparable scenarios, relevant seeds/input traces and a playtest method. Record who will run each check and what observations inform the decision. State player/sample limitations when applicable.

## Check before uncertain expansion

When sample feasibility is uncertain, reuse adequate current evidence or perform the smallest real initialization/fixture check needed to establish availability of the target cohort and required initial conditions before expanding an expensive experiment. If the agreed sample cannot be obtained, record a hold or proposed reframe in the existing record; do not silently substitute agreed seeds or condition an unrelated population to make the sample available.

For a costly matrix or uncertain output size, reuse a pilot's measured bytes and runtime and run a small, risk-selected workload for the affected candidate/policy. Use these observations to estimate chunk and whole-run costs, including retained raw evidence and final serialized reports. Keep measured and estimated costs distinct, and preserve existing runtime/failure guards, limits, failure evidence and required verification. Small normal experiments with adequate current evidence need no additional preflight.

## Execute and compare through existing owners

Assessment owns the hypothesis and evaluation criteria. Planning assigns candidate edits and checks to available owners; assessment does not edit the game. Functional verification checks retained rules, while player observations inform the experience comparison. A missing playtester or runtime leaves that comparison unverified; simulations may still narrow candidates.

Use deterministic checks/simulations for hard constraints and modelled outcomes. A simulated completion rate or valid economy does not establish fun, preference or retention. Record actual playtest method and observations against the exact candidate; do not fabricate play or turn subjective enjoyment into an automatic pass/fail score.

Report baseline versus candidate values, checks, player observations, tradeoffs and adopt/reject/inconclusive recommendation in the existing record. Preserve the rollback values and next action. Adopting a candidate follows existing project authority; an experiment does not silently replace approved live values. Once required verification of a valid comparison is complete, deliver it with its scoped recommendation without waiting for downstream packaging. In the same record, distinguish model comparison, runnable candidate readiness, player observations and product adoption status. A later preparation failure does not erase a valid completed comparison; continue remaining authorized work and keep the overall goal's incomplete state and mandatory gates explicit.

If the change needs new state ownership, persistence, schema or lifecycle semantics, return that portion to technical design and any changed product rules to feature specification. A bounded numerical adjustment under an adequate existing contract does not require new architecture work.
